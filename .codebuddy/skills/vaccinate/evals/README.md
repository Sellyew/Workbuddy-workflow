# 技能评估（evals）——*已验证*与*已测量*之间的那道沟

`./scripts/backtest.sh` 里的门禁证明本仓库**内部自洽、当下为真**。它们不能证明某个技能的指令真的产出好结果。那是另一个断言，需要另一件仪器。

**要分开测两件事。** 看到一个技能被触发，只说明 Claude *找到了*它，不说明它*做了你想做的事*：

| 问题 | 仪器 |
|---|---|
| Claude 是否在它该被触发的提示上调用这个技能——并且不在不该触发时调用？ | 描述触发评估（description-trigger evals） |
| 它真的跑起来时，产出是你想要的吗？ | 输出质量评估（output-quality evals） |

## 方法：基线对照

收集几条真实感强的提示。每一条在**独立会话**里各跑两遍：技能可用时一遍，禁用时一遍。然后比较。独立会话之所以要紧，是因为撰写该技能时残留的上下文会掩盖书面指令里的缺口——你会以为技能写了某句话，其实它只是暗示过。

若带技能那一遍并不更好，这个技能就是在白花上下文。

## 怎么跑

**自带的夹具是主路径。** 从一个普通 shell（**不要**在 WorkBuddy 会话内部——嵌套的无头调用会挂住），在仓库根目录：

```bash
./scripts/run-skill-eval.sh <skill> .codebuddy/skills/<skill>/evals/cases [--replicates N]
```

它先跑行为操纵检查（每条臂都必须通过取回一句标记语来*证明*自己能访问该技能——标记语在 `evals/marker.txt` 里按技能设定），然后在两条臂上分别给每个用例打分，默认 N=3 次重复，**两条臂**都带方差门禁，且每次无头调用都在沙箱里（无 Write/Edit/Bash）。

`skill-creator` 插件是一条可选替代路径，它把一圈更丰富的循环自动化：

```
/plugin marketplace add anthropics/claude-plugins-official
/plugin install skill-creator@claude-plugins-official
```

然后让它去评估一个技能。它把用例存在 `evals/evals.json`，**每个用例派一个子代理**，让每个都从干净状态起步，记录 token 与时长，把断言打分写进 `grading.json`，并把带技能 vs 不带技能汇总进 `benchmark.json`——这样你可以拿通过率的提升去对账 token 与时间成本。

它还做了两件手工最难做的事：对一个技能的**两个版本做盲 A/B**，让你在提交之前确认某次改动确实是改进；以及**描述调优**——生成应触发与不应触发的提示、测命中率，并在技能在错误请求上开火时提出描述修改。

## 先评估哪些技能

按*判断错的代价*排序，而不是按它们跑得多频繁：

1. **`/review-paper --peer`** — 影响投稿决定。
2. **`claim-verifier`** — HIGH-WARN 会让验证以失败闭合。
3. **`/audit-reproducibility`** — 为复现包设门。
4. **`/challenge`** — 它的产出会变成论文里的一条稳健性断言。

## 与 `/vaccinate` 的关系

两者互补，谁也替代不了谁：

- **`/vaccinate`** 问的是*这个检查器能检出我播下的缺陷吗？*——一个关于检查器的**召回**问题。
- **评估**问的是*有了这个技能，产出是否优于没有它？*——一个关于指令集的**质量**问题。

一个技能可以通过评估却仍是个没用的审查者：它产出格式规整、看着可信的发现，却漏掉真缺陷。只有 `/vaccinate` 能抓到这一点。反过来，一个检查器可以认证得很干净，而包着它的技能却在错误的提示上触发。两个都要跑。

## 夹具本身就是一个检查，也必须认证

本仓库里凡是判定工作通过的东西，都必须证明自己能检出一个失败。**评估夹具也在其中。**它的第一版里三个缺陷是靠跑它、而不是靠读它发现的：

| 缺陷 | 症状 | 修法 |
|---|---|---|
| **N=1 次重复** | 同一个用例一次跑出 3/3，十分钟后跑出 1/3——抽样噪声给出了相反的结论 | 默认 `--replicates 3`，并加一个**方差门禁**：单用例标准差 > 0.5 时拒绝出报告 |
| **`nottrigger` 写反了** | 断言某子串必须*存在*，于是无论发生什么都是 1/1，什么也没测到 | `nottrigger-*` 用例现在**取反**：断言必须**不存在** |
| **单子串打分** | 一个换了措辞的正确答案被判为未命中 | 断言列出**多个替代**（`a \| b \| c`）；命中任一即算 |

**断言故意用字面子串。** 让模型去给模型打分，会原样把正在被测量的那个失败重新引进来。替代项让这件事变得可操作，而不必引入一个裁判。

> **不要从一次高方差的运行里记台账行。** 夹具会以退出码 3 结束并说明这一点。在两次运行之间会变的数字不是测量值，把它当成测量值写下来比没有数字更糟——它看起来像证据。

## 成本

每个用例花 `2 x replicates` 次无头运行（带技能与不带技能），每次约 60–90 秒。九个用例在 N=3 下约 54 次运行，远超一小时。按此做预算，且**不要为了抬高覆盖率而机械生成用例**——180 个什么都不测的用例，比 9 个测到东西的更糟，因为台账随后会带着毫无意义的绿行。

## 记录结果

评估结果与资格认证运行记在同一本台账（`quality_reports/qualification/LEDGER.md`），写明技能名、用例数、带与不带技能的通过率、以及 token 差值。**没有记录基线的评估只是一则轶事。**

> **状态（2026-08-22）。** 夹具已通过认证（负控差值 0；正控差值 +2；行为操纵检查），五个优先技能已在 `quality_reports/qualification/LEDGER.md` 里留下记录——包括一个因基线臂噪声大而被夹具扣下的综合分，以及两个照原样记录的近零差值。测到的收益集中在有辨识度的信条上；基线本来就能答的召回型用例测出来约等于 0，所以下一轮迭代要做的是对流程敏感的用例，而不是更多召回型用例。
