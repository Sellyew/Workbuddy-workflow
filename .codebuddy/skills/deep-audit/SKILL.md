# 深度对抗式审计

用并行、收敛式审计替代缓慢的逐轮审查。不要让一个审查者每轮只找出一两个问题，而应同时让多个相互独立的怀疑者检查整个产物并裁定他们的发现。本方法借鉴高难度形式化证明攻关中的多代理实践：组合多样化、全程对抗、只接受具体证据，并反复综合和挑战。

**默认只报告。** 除写入审计报告外，不自动修改被审产物；仅自动应用明确标记 `mechanical: true` 的修复。任何涉及估计目标、假设、设定、推断程序或报告口径的改动都不得标为机械修复，必须先向研究者说明建议及影响并取得批准，再实施和重新验证。

## 什么时候该用它

- 产物内容密集，每次单遍审查仍会冒出新问题，说明逐轮审查不是合适工具。
- 正确性是首要目标，漏掉一个缺陷的代价很高，例如投往顶会或顶刊的论文、证明、安全敏感改动或迁移。
- 用户要求 "fix ALL of it"、"be deeper"、"converge faster"、"100% rock solid"。

用户必须已经选择多代理编排，例如明确要求工作流、深度审计或并行代理，或已经打开 ultracode。如果尚未选择，先提出方案和大致成本。

## 方法

**1. 拆解（多样化组合）。** 按*想法*而不是章节拆解产物，组件可以是独立论断、引理、估计量、子系统或不变量，再加入跨组件的失效模式透镜。目标是让每个关键论断都至少由一个直接针对它的代理检查。不要把自己偏好的理解方式告诉代理，以免破坏独立性，让它们都收敛到同一个看似合理但错误的结论。

**2. 并行派出对抗式查找者，每个组件一个。** 每个查找者都要尝试*反驳*，默认假设「这里有 bug」，并把每项主张落到真实正文或代码上。必须实际阅读，不能凭记忆转述。以下硬规则来自已验证有效的做法：

   - **只接受具体发现。** 每条发现必须包含确切位置（file:line / label + 引文）、一句话缺陷说明和一个**失败用例**，即具体输入/配置 → 错误输出，或确切缺失的假设。
   - **拒收**状态汇报、"looks fine"、"this is standard/routine"、含糊的乐观判断，以及 "the global step is straightforward."。
   - **把同一困难转移到别处或预设结论的修法不算修复**，应明确标出。
   - 如果认真攻击后没有发现问题，代理必须列出实际执行过的具体攻击，以及每次攻击为何未能推翻产物，不能只说 "clean"。

**3. 由独立裁判逐条裁定。** 裁判重新打开每个被引用位置，对产物和发现都保持怀疑，判定 CONFIRMED / REFUTED / DOWNGRADED。这一步用于排除假阳性，例如误读、假设其实已在别处给出、失败用例在所述条件下不会发生，从而保证修复清单可靠。

**4. 综合。** 按位置去重，按 fatal > major > minor 排序，形成清晰的缺陷清单。任何内容在通过这一步之前都不能算作问题。

**5. 默认报告，分级修复并重新验证。** 所有已确认项先进入报告；仅 `mechanical: true` 的项可自动应用。涉及估计目标、假设、设定、推断或报告口径的项必须等待研究者明确批准，不得因为用户要求“全部修复”就跳过这项批准。实际改动后，重新审计被改动的位置，确认修复没有引入新缺陷。按波次重复，直到**连续两轮**审计均无新增发现；未获批准的非机械项保持开放并明确列出，不得宣称产物已无缺陷。兜底上限为 5 波；同一发现若在波次 N 和 N+2 都存在，应交给用户，不要第三次打补丁。第一波结束后不能停止。

## 失效模式透镜（按领域调整）

除逐组件攻击外，还要明确检查以下跨组件模式，真正的缺陷常藏在这里：

- **过度声称：** 标题或摘要的断言超过定理或检验实际支持的范围。
- **证明中的越界：** 需要*一致*结论时使用*逐点*结论；不加限定地陈述一个*双向都成立*的性质；把特例论证当作一般论证。
- **沉默的假设：** 数学中使用却未陈述的可微、稠密、连续、有界或正值条件；代码中未经检查的前置条件或不变量。
- **边界情形：** 原子/并列、端点/无界支撑、空/退化输入、参数空间边界。
- **循环：** 假设预设自身结论；结果引用自身；引文不足以支持断言，必须实际阅读被引文献。
- **内部矛盾：** 同一处定义或记号有两种用法；表格单元与命题冲突；正文和附录不一致；交叉引用悬空或错误。

## 全新眼光一遍（终闸）

每轮定向审计都会继承提示词作者的盲点。聚焦提示、修复历史和预期失效模式都会把审计者引向已知区域。因此，**完成所有定向波次和修复后，再运行一次几乎不提供上下文的冷启动审计。** 为待审产物制作仓库外的中立副本，只把该副本和一句极简指令（"find concrete defects: location + failing case"）交给独立审计 Agent，不提供聚类分配、历史或重点关注清单。该 Agent 的工作目录和工具权限必须使其**无法读取、搜索或遍历本仓库**，包括 Git 历史、技能、规则、日志和先前评审；若不能强制执行这种隔离，就停止冷启动终闸并请求隔离运行环境，不能把普通 fresh context 当作满足条件。只让入口保持多样，例如像期刊审稿人一样从正文开始、从附录开始、从表格或论断开始，以及由审计者自选一个位置深入检查。发现仍照常裁定。

收口需要同时满足：全新眼光审计无发现、定向覆盖无发现、机械检查组全绿。如果全新眼光发现定向波次遗漏的问题，这也说明提示词存在缺陷，应把遗漏的失效模式补入透镜。

## 全量清单——绝不抽样

对于论文或证明类产物，**先列全每条形式化陈述**，用正确转义的扩展正则枚举环境，再枚举对应标签：

```bash
grep -E '\\begin\{(theorem|proposition|lemma|corollary)\}' <file.tex>
```

为每条陈述和每个证明指派验证者，关键陈述的覆盖必须达到 100%，不能只审查者挑选的少数证明。机械建立“陈述 → 标签 → 验证者 → 已返回报告”的对账表，分别报告枚举陈述数、标签覆盖数、验证者指派覆盖数、唯一验证者数和已返回报告所覆盖的陈述数；枚举、标签与验证者指派必须逐条对应，返回覆盖数必须等于指派覆盖数，任何缺标签、缺指派或未返回都使覆盖检查失败。抽样只能线性、随机地收敛，完整清单则能在一波内覆盖。

把紧耦合的小引理归成簇，大证明单独配置验证者；聚簇时保留多对一映射，不能用唯一验证者较少来掩盖未覆盖陈述。除审查发现外，每个验证者还要返回**已验证步骤清单**和**假设台账**，区分用到与已陈述的假设；用到但未陈述即构成一条发现。

## 机械检查组（产出最高的检查）

书面论证可能读起来严密，但它定义的对象却可能有误。对**每个估计方程、影响函数恒等式、识别论断和总体矩**，都编写一个可执行检查，在对抗式玩具设计中计算相应总体对象。设计应覆盖截断（删失端点位于结果端点之下）、内部原子、错误设定的干扰项、边界或重叠失败，并用数值方式断言所声称的中心化或恒等关系，可采用解析方法，或固定种子的细网格/大 N。

把这些脚本保留为仓库中的常设测试目录并配 README，相应公式变更后立即重跑。一段五行的总体计算就能发现整类缺陷，例如尾部重归一化的根、符号翻转和质量亏空加权；仅靠细心阅读或模型共识并不可靠。

## 修复卫生

- **修复引入的新数学尚未经过审计。** 每波修复后，都要针对恰好被修改的位置追加一波验证，然后才能宣布收口。
- **在工作流综合中按 INDEX 配对发现与判定**，要求裁判按发现顺序返回判定。绝不按位置字符串配对，因为裁判可能改写位置，导致发现静默丢失。动手前，先把综合摘要与日志核对一遍。

## 走不通的路也是结果

如果某组件在所述假设下无法修复，这本身就是一条发现，不表示审计失败。报告还缺什么，例如精确缺失的假设或断掉的步骤，并给出诚实选项：削弱论断、补上假设或收窄范围。不要寻找更有利的解读，也不要让代理把定理强度缺口写成 "routine"。

## 编排

- 在一条消息中通过并行 `Agent` 调用派出查找者，每个组件一个；随后为每个组件配置一名裁判，裁定该组件的发现，再做综合。见 [`orchestrator-protocol.md`](../../rules/orchestrator-protocol.md)。Workflow 工具可用时，例如 `ultracode` 会话，`pipeline(components, finder, judge)` 是可选加速器，可以在查找者返回后立即裁定该组件发现，无需等待全部查找者；它绝不是必需项。返回已确认清单后，默认只报告；自动修复仅限 `mechanical: true`，其余按上述研究者批准规则处理。
- **模型分工：** 查找者使用强的执行/分析模型，负责寻找和攻击问题；裁判者使用强的裁定模型。遵循 [`model-routing.md`](../../rules/model-routing.md) 的本地约定，这里两个角色都固定为 `reasoning` 档。若要让查找者思考更深，给它 `effort: high`；`effort:` 在代理 frontmatter 中有效。**不要写「上 Fable 层」**，本平台没有第四个模型层。每个组件保留一名裁判，一次裁定该组件的全部发现，以节省裁定预算。
- 把查找者固定为 `reasoning` 档，并给它确切标签或位置，以及具体攻击清单。
- **持续追查。** 不要返回 "best effort"，也不要只列出「为什么难」。返回已确认缺陷和修复建议；仅对自动应用的机械修复或研究者已批准的改动给出复审，未批准项保持开放。如果仍有缺口，准确说明最强的剩余问题，不得给出无缺陷结论。

## 提示词骨架

查找者：*"你是一名敌意审稿人，正在审计一个组件。读 {locations} 处实际的文本。攻击：{failure modes}。只返回具体的发现（位置 + 缺陷 + 失败用例）；不要 'looks fine'/'routine'/含糊。把困难挪到别处的修法不是修法。若判定干净，列出你跑过的具体攻击以及每一次为何闭合。"*

裁判者：*"一名对抗式审稿人就组件 X 返回了这些发现。对每一条，打开所引位置，对照文本实际说了什么及其证明做核实，标记 CONFIRMED/REFUTED/DOWNGRADED。对产物与发现两者都保持怀疑。"*

## 共享信条只写在一处

本审计依赖以下三条规则，但不在此重复定义，因为其他验证面也使用同一套规则，再写一份容易产生漂移：

- **播种故障校准**：从未检出植入缺陷的检查不能为产物背书。→ [`/vaccinate`](../vaccinate/SKILL.md) 和 [`verification-ladder.md`](../../references/verification-ladder.md) rung 0。
- **独立性与相关误差**：模型间一致不等于确证，它们可能以相同方式失败。→ [`verification-ladder.md`](../../references/verification-ladder.md) rung 3。
- **五个可信度问题**：其中一个问题的证据不能清除另一个问题。→ [`external-oracle-process.md`](../../references/external-oracle-process.md) §6。
