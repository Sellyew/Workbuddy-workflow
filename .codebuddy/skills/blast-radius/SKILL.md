# 动手之前，先弄清影响半径

危险的改动不是那个看起来有风险的。是那个**看起来纯粹是增量**的——加一个返回值、一列、一个选项——却在三个文件之外悄悄违反一份没人重读过的契约。编译与类型检查抓不住位置或长度上的契约；你要么在离改动很远的地方崩掉，要么更糟：产出悄悄算错的输出。

**规则：改了共享接口，就把它的消费者跑起来。读它们不等于跑它们。**

## 1. 编辑之前先枚举消费者

grep 每一处调用点、import 与下游引用——含测试、notebook、脚本、文档，以及任何会重新生成被报告结果的东西。标出哪些产出的数字会出现在论文、看板或发布里：那些是静默破坏代价最高的。

若某个消费者在另一个仓库、另一种语言，或一个生成出来的产物里，现在就写下来；到了核验的时候你不会记得。

**另一个仓库里的消费者是靠 commit SHA 钉住本仓库的。**它的核验收据记录的是它构建时所依据的*版本*——不是一个分支，不是一个版本字符串，这两者都会在它脚下继续移动。所以**这里一个会移动下游所报告数字的改动，在本仓库变绿时并没有结束**：什么移动了的前后证据、下游产物的重新生成，以及重新钉住，全都属于和这次改动*同一轮*——[`release-engineering.md`](../../references/release-engineering.md) §6 有它们之间的先后顺序。一个被留在旧 SHA 上的下游是一种诚实、可检查的状态；一个被指向移动引用的下游则会悄悄继承一个没人重新核过的数字。

## 2. 点名你即将改动的契约

明确地问：下游代码有权假定什么：

- **元数／长度**——有谁按位置索引、对着一个定长清单 zip、或预分配一个已知宽度的矩阵？*加一个元素，这三样全破。*
- **名称与顺序**——有谁按名字匹配、按位置匹配，或把你的输出与一份另行的平行标签清单配对？
- **类型、单位、量纲**——元还是分，比率还是百分比，秒还是毫秒，0 起索引还是 1 起索引。
- **可空性与哨兵值**——消费者不会预期的新空值／NA 情形。
- **默认值**——改一个默认值，会悄悄改动每一个依赖它的调用方。
- **同一性／排序保证**——行序、排序稳定性、键唯一性。

经典的失败：一个返回向量从 6 个元素长到 7 个，而某个消费者把它与一份写死的 6 个标签清单配对。改动处什么错都不报；消费者要么在很远的地方抛错，要么更糟：循环复用，把每一行都贴错标签。

## 3. 优先选不会破坏契约的改法

按名字的增量胜过按位置的增量。在你能控制消费者的地方，按名字匹配而不是按位置。在你不能的地方，给接口升版，而不是就地加宽它。

**不要**在旧标签本来就是刻意不同的时候，用从新数据推导标签／配置的方式去「修」一个不匹配——刻意的重贴标签是存在的（显示名与内部名不同），而自动推导会悄悄改变已发布的输出。

## 4. 跑消费者——端到端，用真实输入

一个只是 import 了的消费者不算被行使过。每种不同的消费者模式至少跑一条完整路径，优先选那条会重新生成被报告数字的。

然后**两个方向**都核验：
- 新东西能用。
- **旧东西没变。**diff 之前报告过的输出；任何移动了的东西都必须有一个你说得出的理由。若这次改动本应是保持行为的，那证据是逐字节相同或在声明过的容差之内——不是「它跑过了」。

## 5. 什么都没跑的话，绿是不提供信息的

确认这项检查真的执行了、而且有可能失败：一个被跳过的测试、一个被过滤掉的用例、一个被吞进默认值的异常、一个在比对之后被放宽的容差，在日志里都和成功无法区分。当改动影响重大时，**播一个缺陷进去**，确认检查变红——一个不会失败的比对不是证据。

## 6. 记录契约改动

若接口确实变了，就在消费者会看的地方说出来：一条 NEWS/CHANGELOG 条目、一条带版本的接口说明，或定义处一条点名下游代码可以假定什么的注释。对任何会被复用或发布的东西，冻结输入（版本、哈希、种子）并记录声明过的容差，好让下一次比对是可复现的，而不是重新谈判的。

## 最小检查清单

1. grep 所有消费者，含测试、脚本、文档、其他仓库／语言。
2. 写下契约：元数、名称、顺序、类型、单位、默认值、排序。
3. 能按名字／版本改的地方就按名字／版本改。
4. 每种消费者模式至少跑一条完整路径。
5. diff 之前报告过的输出；解释任何移动。
6. 播一个缺陷，证明这项检查会失败。
7. 在消费者看得见的地方记录契约改动。
8. 把每个跨仓库消费者重新钉到新 SHA——在本轮重新生成并重新核验，不是下一轮。
