# 计划先行工作流

**在触及三个以上文件、或改变某项交付物实质内容的任务之前，进入计划模式**（一讲课件、一份稿件、一条分析流水线、一个复现包）。小而明确的编辑直接做——为它们做计划，成本高于收益。

## 流程

1. **进入计划模式** —— 使用 `EnterPlanMode`
2. **查 MEMORY.md** —— 读与本任务相关的 `[LEARN]` 条目
3. **需求规格（用于复杂／含糊的任务）** —— 见下文
4. **起草计划** —— 改什么、哪些文件、按什么顺序
5. **存到磁盘** —— 写入 `quality_reports/plans/YYYY-MM-DD_short-description.md`
6. **呈现给用户** —— 等待批准
7. **退出计划模式** —— 仅在获批之后
8. **保存初始会话日志** —— 趁记忆新鲜记下目标与关键上下文
9. **通过编排器实施** —— 见 `orchestrator-protocol.md`

## Step 3：需求规格（用于复杂／含糊的任务）

**何时使用：**
- 任务比较高层或含糊（「改进这一讲」「分析这份数据」）
- 存在多种合理读法
- 需要可观投入（>1 小时或 >3 个文件）

**何时跳过：**
- 任务清楚具体（「修掉第 42 行的错字」）
- 简单的单文件编辑
- 用户已经给出详细需求

**流程：**
1. 用 AskUserQuestion 澄清含糊之处（最多 3-5 个问题）
2. 用 `templates/requirements-spec.md` 创建 `quality_reports/specs/YYYY-MM-DD_description.md`
3. 为每条需求标注：
   - **MUST**（不可让步）
   - **SHOULD**（优先）
   - **MAY**（可选）
4. 为每个主要方面声明清晰度状态：
   - **CLEAR：** 已完全规定
   - **ASSUMED：** 合理假设（用户可否决）
   - **BLOCKED：** 未获答复前无法推进
5. 就规格获得用户批准
6. 然后才进入 Step 4（起草计划），以规格为输入

**模板：** `templates/requirements-spec.md`

**为什么有用：** 在计划**之前**抓住含糊之处。把计划中途的转向减少 30-50%。

## 计划落在磁盘上

计划能在上下文压缩后存活。每一份计划都保存到：

```
quality_reports/plans/YYYY-MM-DD_short-description.md
```

格式：状态（DRAFT/APPROVED/COMPLETED）、做法、要修改的文件、核验步骤。

## 上下文管理

### 一般原则
- 在一个任务之内，让压缩带着你走 —— 用 `/compact <what to keep>` 引导它
- 在不相关的任务之间，`/clear`
- 在重要上下文丢失之前把它存到磁盘
- 要停下或交接：`/checkpoint`、退出，然后新起一个 `claude` —— 会话交接钩子会把最新的检查点交给下一次全新启动，只给一次（不会给 `--continue` /
  `--resume`）；之后就请 Claude 读那个检查点文件

### 上下文存活策略

**自动压缩之前：**
接近上下文上限时，确保：
1. MEMORY.md 已收进本次会话的全部 `[LEARN]` 条目
2. 会话日志是最新的（10 分钟内更新过）
3. 在用的计划已存到磁盘
4. 悬而未决的问题已记入会话日志

压缩钩子自己会把状态带过去：`pre-compact.py` 保存在用的计划、当前任务和最近的决策，`post-compact-restore.py` 之后再注入回来。它们只能恢复磁盘上有的东西 —— 让计划和会话日志保持最新，才是恢复出来的状态准确的原因。

**压缩之后：**
第一条消息应当是：「压缩后继续。上一个任务：[读最近一份计划 + git log]。状态：[下一步]。」

## 会话恢复

压缩之后或新会话中：
1. 读 `CODEBUDDY.md` + `quality_reports/plans/` 里最近的一份计划
2. 看 `git log --oneline -10` 和 `git diff`
3. 说出你所理解的当前任务是什么
