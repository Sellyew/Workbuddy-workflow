# 计划先行工作流

**任务如果涉及超过三个文件，或会改变某项交付物的实质内容，必须先进入计划模式。**交付物可以是一讲课件、一份稿件、一条分析流水线或一个复现包。小而明确的编辑直接完成，不必为它们承担额外的计划成本。

## 流程

1. **进入计划模式**：使用 `EnterPlanMode`。
2. **查 MEMORY.md**：阅读与本任务相关的 `[LEARN]` 条目。
3. **需求规格（用于复杂／含糊的任务）**：见下文。
4. **起草计划**：写明改什么、涉及哪些文件、按什么顺序执行。
5. **存到磁盘**：写入 `quality_reports/plans/YYYY-MM-DD_short-description.md`。
6. **呈现给用户**：等待批准。
7. **退出计划模式**：只有获批后才能退出。
8. **保存初始会话日志**：趁记忆清晰，记录目标和关键上下文。
9. **通过编排器实施**：见 `orchestrator-protocol.md`。

## Step 3：需求规格（用于复杂／含糊的任务）

**何时使用：**
- 任务比较高层或含糊，例如「改进这一讲」「分析这份数据」。
- 存在多种合理读法。
- 需要可观投入，即 >1 小时或 >3 个文件。

**何时跳过：**
- 任务清楚具体，例如「修掉第 42 行的错字」。
- 只需简单的单文件编辑。
- 用户已经给出详细需求。

**流程：**
1. 用 AskUserQuestion 澄清含糊之处，最多问 3-5 个问题。
2. 用 `templates/requirements-spec.md` 创建 `quality_reports/specs/YYYY-MM-DD_description.md`。
3. 为每条需求标注优先级：
   - **MUST**（不可让步）
   - **SHOULD**（优先）
   - **MAY**（可选）
4. 为每个主要方面声明清晰度状态：
   - **CLEAR：**已完全规定。
   - **ASSUMED：**采用合理假设，用户可以否决。
   - **BLOCKED：**未获答复前无法推进。
5. 请用户批准规格。
6. 获批后才进入 Step 4，以规格为输入起草计划。

**模板：** `templates/requirements-spec.md`

**为什么有用：**在制定计划**之前**发现含糊之处，可把计划中途的转向减少 30-50%。

## 计划落在磁盘上

把计划写入磁盘，即使发生上下文压缩也能保留。每份计划都保存到：

```
quality_reports/plans/YYYY-MM-DD_short-description.md
```

计划格式包括状态（DRAFT/APPROVED/COMPLETED）、做法、要修改的文件和核验步骤。

## 上下文管理

### 一般原则
- 在同一任务中需要压缩时，用 `/compact <what to keep>` 指明要保留的内容。
- 切换到不相关的任务时，使用 `/clear`。
- 在重要上下文丢失之前，把它写入磁盘。
- 需要停下或交接时，先执行 `/checkpoint`，再新建一个任务。会话交接钩子会把最新检查点交给下一个全新会话，而且只递交一次；接续旧任务时不会递交。之后让 WorkBuddy 读取该检查点文件。

### 上下文存活策略

**自动压缩之前：**
接近上下文上限时，确保：
1. MEMORY.md 已收进本次会话的全部 `[LEARN]` 条目。
2. 会话日志在 10 分钟内更新过。
3. 在用的计划已写入磁盘。
4. 悬而未决的问题已记入会话日志。

压缩钩子会传递已有状态：`pre-compact.py` 保存在用的计划、当前任务和最近的决策，`post-compact-restore.py` 随后再注入这些内容。钩子只能恢复磁盘上已有的信息，因此只有及时更新计划和会话日志，恢复的状态才准确。

**压缩之后：**
第一条消息应当是：「压缩后继续。上一个任务：[读最近一份计划 + git log]。状态：[下一步]。」

## 会话恢复

压缩后或新会话中：
1. 读取 `CODEBUDDY.md` 和 `quality_reports/plans/` 中最近的一份计划。
2. 查看 `git log --oneline -10` 和 `git diff`。
3. 说明你对当前任务的理解。
