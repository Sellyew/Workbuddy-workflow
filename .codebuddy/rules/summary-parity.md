# 摘要与正文一致（反打地鼠）

**编辑任何摘要段落时，不要做外科手术式的词级修补。**正文改动后没有重新核对摘要，两者就会漂移。只修改被点名的词语，几乎总能在同一段的其他地方留下或引入新的漂移。

## 什么算「摘要段落」

- CHANGELOG 中某个版本条目的开篇段落，即第一个 `###` 子标题之前的导语
- README.md 的标语与各节导语
- PR 标题与 `## Summary` 块
- 技能 / 规则 / 代理 frontmatter 的 `description:` 字段
- 指南 `workflow-guide.qmd` 的各节摘要
- MEMORY.md `[LEARN:*]` 条目的标题行，即正文之前的单句总结
- 任何形如「本次发布做了 X。它没做 Y。计数是 Z。」的段落，这类三段式断言很容易漂移

## 流程

编辑摘要段落时，或者审阅者点名摘要段落时，无论审阅者是人、Copilot 还是 Codex，都要执行以下流程：

1. **读完整个正文**，也就是摘要所概括的全部内容，不能只看 diff。
2. **枚举当前摘要中的每一条实质断言**，包括每个名词清单，如「技能、规则、钩子」，每个数字，每个最高级断言，如「没有新增」，以及每处包含或排除，如「除 X 之外」。
3. **逐条对照正文核查。**为每条断言找到支持或反驳它的正文内容。
4. **改整段，而不是只改被点名的短语。**任何站不住脚的具体断言都必须就地更正。
5. **重新扫描两侧的孤立引用，确保摘要和正文中都没有失去对应内容的表述。**

## 何时停止打补丁、改为重写

如果审阅者对同一摘要段落**连续两次**点名，即使指出的是不同词语，也要停止打补丁，从结构上重写。重复点名说明段落的组织方式有问题，而不只是措辞有问题。

**重写偏向：**摘要里宁要抽象，不要具体。不作枚举性断言的摘要，不会因枚举项变化而漂移。

| 易漂移（具体） | 抗漂移（抽象） |
|------------------------|------------------------|
| 「没有新技能、没有新规则、没有新钩子」 | 「磁盘上没有新目录」 |
| 「27 个技能 / 13 个代理 / 22 条规则 / 6 个钩子」 | 「磁盘清单未变，计数见 README」 |
| 「改动了 `.codebuddy/agents/X.md` 与 `.codebuddy/skills/Y/SKILL.md`」 | 「既有基础设施经修订」 |
| 「修复 Copilot 发现 #3 与 Codex 发现 #7」 | 「处理合并前审读」 |

具体写法在刚写完时信息量更大，却更容易过时；抽象写法能在多次编辑后继续保持为真。

## 教训：Copilot / Codex 是漂移探测器

审阅机器人反复发现同一段落的问题时，应把它视为**结构信号**，而不是一份需要逐项打补丁的 bug 清单。每次补丁只能缩小当前的漂移窗口，正文的下一次编辑仍会在别处打开新窗口。

## 两次即止的模式是通用的

「被点两次 → 停止打补丁，升级处理」不只适用于摘要。只要每轮都能暂时掩盖分歧，却没有真正解决分歧，就适用这条规则：

- `review-paper --adversarial`：第 N 轮与第 N+2 轮提出同一个关切时，会标记给用户，而不是第三次打补丁。
- `audit-reproducibility`：一条数值断言连续两次审计都被降级为 **EXPLAINED**，却从未更正为 PASS，就会显著浮出，并显示 "contested number EXPLAINED twice, never corrected"，而不是藏在已记录的备注后面。

这些情形中的两次即止，都说明*产物的组织方式不对*，而不是措辞还需微调。

## 交叉引用

- `MEMORY.md`：关于摘要与正文反复漂移的 `[LEARN:audit]`，保留逐断言核对与结构性重写原则。
- `.codebuddy/skills/commit/SKILL.md`：为文档为主的 PR 写提交信息时，在推送前把本规则应用于 `## Summary` 部分。
- `.codebuddy/skills/audit-reproducibility/SKILL.md`："Repeated EXPLAINED is a signal (two-strikes)" 把这一模式用于有争议的数值断言。
