# 问题台账——已确认缺陷的证据标准

把 issue tracker 当作**已确认缺陷的持久台账**。目的不是让 issue 数量最大化，
而是确保一个缺陷、它的证据、它的修复，以及**那项修复的边界**，不会消失在某个
分支、某个聊天窗口或某条提交讯息里。

只活在对话里的缺陷，是你将来还会再发现一遍的缺陷。

## 什么情况开 issue

tracker 是项目跨会话、跨机器的记忆，所以该比一次会话活得更久的工作都
放进去：

| 情形 | 开 issue？ |
|---|---|
| 主分支上代码或文档里的缺陷，或任何人报告的缺陷 | 是——在修复**之前**开，并按下面的标准写 |
| 值得做但眼下不做的改进 | 是——打上 `enhancement` 标签，而不是往本地 backlog 文件里加一行 |
| 属于 owner 且阻塞工作的决定 | 是——写明这个决定，以及什么在等它 |
| 针对未合并分支的一轮审查（很多发现，合并前全部修完） | 这一轮开一个汇总 issue，带一份已确认发现的清单，随 pull request 一起关闭 |
| 你在同一次未合并改动里犯下并修好的错误 | 否——提交和 pull request 已经记录了 |

**绝不要把受限数据放进 issue**——不要放受数据使用协议覆盖的数据的任何取值、标识符、
文件路径或截图（[`confidential-data.md`](confidential-data.md)）。抽象地描述缺陷；
证据留在数据所在的地方。

## 何时开

当一个有边界的检查确认某种行为违反了书面契约、统计法则、不变量、可复现性
要求或对用户的承诺时，**每个根因开一个 issue**。先搜开着的*和*已关闭的
issue；把相关症状链接起来，而不是重复开。在本模板里这个搜索是强制执行
的：新 issue 通过 `scripts/file-issue.py` 创建，它会跑若干次搜索并把结果
记进 issue 正文，而 `issue-guard` 钩子会拒绝裸的 `gh issue create`
（[`/issues`](../skills/issues/SKILL.md)）。

初次报告必须带上：

- 确切的**源码版本**、分支与工作树；
- **观察到的行为 vs 预期的行为**；
- 一个**最小复现器**，或一件留存下来的证据产物；
- **测量的分母**、未解决的案例，以及一个**活的阳性或阴性
  对照**——「962 个值里有 430 个变了」，而不是「有些值变了」；
- **科学后果**——它威胁到哪一条断言；
- **受影响范围，以及明确的不受影响范围**；
- **可度量的验收标准**。

> **不要悄悄修好一个已确认的缺陷。**无声的修复毁掉「哪里错、为什么错」的记录，
> 下一个人就分不清一次有意的改动和一次回归。

> **不要把猜测当作既定事实提交。**在正文里标出不确定之处，并写明
> 将由哪个有边界的检验来裁定。

## 分诊

**改代码之前，先在指明的版本上复现。**如果后续证据改变了诊断，就在 issue 里更正它——
并把**旧诊断保留下来**作为审计痕迹的一部分。一个被推翻的假设，是关于
系统如何误导人的证据。

修复、它的测试、以及任何必需的审计未完成期间，issue 保持打开。

**不要用自动关闭关键词**（`Closes`、`Fixes`、`Resolves`）写进提交或 PR。
自动关闭会抢在最新科学判断之前——合并是一次代码事件，关闭则是一个*判断*。
最终的状态转换是手工的。

对承重数值面的改动，要跑聚焦测试、失败即关闭的审计夹具、
不变量指纹比对，以及全量测试套件。**绝不要只为拿到绿色门禁就重新
认可一个变了的指纹；先给每一处变动归因**
（[`provenance-and-ground-truth.md`](../references/provenance-and-ground-truth.md)）。

## 关闭评论

以完成状态关闭之前，发一条最终评论。对于可能动摇一个结果、一个数字或一项
对用户承诺的缺陷，它要包含下面全部七节。对于小修——一个错字、
一句过时的话、一个坏链——一条短评论就够：错在哪、哪个提交修的、
你怎么核对的。

七节如下：

1. **更正后的诊断与根因。**实际错在哪里，以及
   测量推翻了先前哪个假设。
2. **修复身份。**确切的提交；有实质改动的文件或函数。
3. **改前 → 改后。**修复前后的测量值，*带分母*、缺失案例、
   阈值，以及留存产物的路径或哈希。
4. **对照。**阳性、阴性、变异或回归对照，用来证明门禁
   **仍能因预期原因失败**——顺带把检测器关掉的修复
   不算修复。
5. **验证。**聚焦测试，加上全量套件的文件数 / 通过 / 失败 / 错误 / 警告 / 跳过
   计数。对数值面，给审计判定与指纹，或说明为何不适用。
6. **性能。**若是性能问题：可比的改前/改后耗时，
   硬件与运行时环境、看门狗状态。
7. **边界与后续。**未测试的路径、推迟的决定、相关 issue。

**先发评论。对照验收标准重读一遍。然后手工关闭。**

## 其他处置

- **重复**——指出作为正本的那个 issue，并说明为什么根因相同。
- **不计划 / 已被推翻**——贴出裁定证据，说明为何无需修复。**失败的假设
  是有用的证据，要留在明面上。**
- **拆分范围**——原件保持打开，直到其验收标准通过，或明确带理由地修改
  它们。**绝不要用后续 issue 来掩盖一条未满足的原始标准。**
- **回归**——当*同一根因*回来时重开既有 issue；当症状有不同根因
  时开新的。

## 审计规则

在每个成型的检查点上，对着当前源码分诊新的审查线程。**抓取失败
不等于收件箱为空。**审查工具绝不能自动回复或自动标为解决。

任何交接之前，核实这一轮发现的每个缺陷，要么有开着的 issue 代表它，
要么有一个已完成的 issue、其最终评论达到上面的关闭标准——能动摇一个结果、
一个数字或对用户承诺的缺陷要七节齐全，
小修则用短格式。例外情况写进交接，而不是悄悄改掉
issue 状态。
