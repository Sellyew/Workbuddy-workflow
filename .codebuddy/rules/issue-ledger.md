# 问题台账——已确认缺陷的证据标准

issue tracker 是**已确认缺陷的持久台账**。它的作用不是增加 issue 数量，而是长期保留缺陷、证据、修复和**修复边界**，避免这些信息只存在于某个分支、聊天窗口或提交讯息中。

只记录在对话里的缺陷，将来很可能还要重新发现一次。

## 什么情况开 issue

tracker 保存项目跨会话、跨机器的记忆，因此，凡是需要比一次会话活得更久的工作，都应写入 tracker：

| 情形 | 开 issue？ |
|---|---|
| 主分支上代码或文档里的缺陷，或任何人报告的缺陷 | 是——在修复**之前**开，并按下面的标准写 |
| 值得做但眼下不做的改进 | 是——打上 `enhancement` 标签，而不是往本地 backlog 文件里加一行 |
| 属于 owner 且阻塞工作的决定 | 是——写明这个决定，以及什么在等它 |
| 针对未合并分支的一轮审查（很多发现，合并前全部修完） | 这一轮开一个汇总 issue，带一份已确认发现的清单，随 pull request 一起关闭 |
| 你在同一次未合并改动里犯下并修好的错误 | 否——提交和 pull request 已经记录了 |

**绝不要把受限数据放进 issue。**受数据使用协议约束的数据，其取值、标识符、文件路径和截图都不得写入 issue（[`confidential-data.md`](confidential-data.md)）。请抽象描述缺陷，把证据留在数据所在的位置。

## 何时开

有边界的检查一旦确认某种行为违反书面契约、统计法则、不变量、可复现性要求或对用户的承诺，就要**为每个根因分别开一个 issue**。先搜索开放和已关闭的 issue，链接相关症状，不要重复登记。本模板强制执行这项搜索：新 issue 必须通过 `scripts/file-issue.py` 创建，脚本会执行多次搜索并把结果写入 issue 正文；`issue-guard` 钩子会拒绝直接调用 `gh issue create`（[`/issues`](../skills/issues/SKILL.md)）。

初次报告必须包含：

- 确切的**源码版本**、分支与工作树；
- **观察到的行为 vs 预期的行为**；
- 一个**最小复现器**，或一件留存下来的证据产物；
- **测量的分母**、未解决的案例，以及一个**有效的阳性或阴性对照**。例如，写「962 个值里有 430 个变了」，不要写「有些值变了」；
- **科学后果**，即它威胁到哪一条断言；
- **受影响范围，以及明确的不受影响范围**；
- **可度量的验收标准**。

> **不要悄悄修好一个已确认的缺陷。**无声的修复会抹掉「哪里错、为什么错」的记录，使下一个人无法区分有意改动与回归。

> **不要把猜测当作既定事实提交。**在正文中标明不确定之处，并写明将由哪项有边界的检验作出裁定。

## 分诊

**修改代码前，先在注明的版本上复现。**后续证据如果改变诊断，就在 issue 中更正，同时**保留旧诊断**作为审计记录。被推翻的假设也能说明系统如何误导人。

修复、测试和所有必要审计完成前，issue 必须保持开放。

**不要在提交或 PR 中使用自动关闭关键词**（`Closes`、`Fixes`、`Resolves`）。合并只是代码事件，关闭则需要*判断*；自动关闭可能抢在最新科学判断之前。最终状态必须由人工变更。

修改承重数值面时，要运行聚焦测试、失败即关闭的审计夹具、不变量指纹比对和全量测试套件。**绝不要只为让门禁通过就重新认可已经变化的指纹；必须先解释每一处变动的原因**（[`provenance-and-ground-truth.md`](../references/provenance-and-ground-truth.md)）。

## 关闭评论

以完成状态关闭 issue 前，必须发布最终评论。缺陷如果可能影响结果、数字或对用户的承诺，评论必须包含以下七节。错字、过时表述、坏链等小修只需一条短评论，说明错在哪里、由哪个提交修复，以及如何核验。

七节如下：

1. **更正后的诊断与根因。**说明实际错误，以及测量推翻了哪个先前假设。
2. **修复身份。**给出确切提交，以及发生实质改动的文件或函数。
3. **改前 → 改后。**列出修复前后的测量值，*包括分母*、缺失案例、阈值，以及留存产物的路径或哈希。
4. **对照。**使用阳性、阴性、变异或回归对照，证明门禁**仍能因预期原因失败**。如果修复顺带关闭了检测器，就不算真正修复。
5. **验证。**运行聚焦测试，并给出全量套件的文件数、通过、失败、错误、警告和跳过计数。数值面还要给出审计判定与指纹，或说明为何不适用。
6. **性能。**如果是性能问题，给出可比较的改前、改后耗时，以及硬件、运行时环境和看门狗状态。
7. **边界与后续。**列出未测试的路径、推迟的决定和相关 issue。

**先发布评论，对照验收标准重新阅读，再手工关闭。**

## 其他处置

- **重复**：指出作为正本的 issue，并说明为什么根因相同。
- **不计划 / 已被推翻**：附上裁定证据，说明为何无需修复。**失败的假设是有用证据，必须公开展示。**
- **拆分范围**：原 issue 保持开放，直到满足验收标准，或明确说明理由并修改验收标准。**绝不能用后续 issue 掩盖尚未满足的原始标准。**
- **回归**：*同一根因*再次出现时，重开原 issue；症状相同但根因不同时，另开 issue。

## 审计规则

在每个成型的检查点，根据当前源码分诊新的审查线程。**抓取失败不等于收件箱为空。**审查工具绝不能自动回复，也不能自动把线程标为已解决。

交接前，必须核实本轮发现的每个缺陷都有对应记录：要么有一个开放的 issue，要么有一个已完成的 issue，且其最终评论符合上述关闭标准。可能影响结果、数字或对用户承诺的缺陷必须写全七节，小修可以使用短格式。例外情况要写入交接，不能通过悄悄修改 issue 状态来掩盖。
