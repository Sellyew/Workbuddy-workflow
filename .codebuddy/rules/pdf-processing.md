# 稳健的 PDF 处理

**默认直接读取 PDF。**Read 工具原生支持 PDF。论文超过约 10 页时，传入 `pages` 范围，例如 `pages: "1-20"`，每次请求最多 20 页。1M token 的上下文窗口足以宽裕地容纳一篇完整论文，因此**不需要**预先把普通论文切成片段文件。

## 工作流

**Step 1：先查大小**
```bash
pdfinfo paper_name.pdf | grep "Pages:"
ls -lh paper_name.pdf
```

**Step 2：直接读**
- **普通论文（最多约 100 页）：**用 Read 工具读取，通过 `pages` 参数翻页，每次请求最多 20 页，无需预先切分。
- **有选择的深读（这是成本优化，不是容量上限）：**读长论文时，可以逐节扫读，细读识别策略、方法、结果等承重部分，略读附录／参考文献。这样做是为了节省 token，不是因为模型无法容纳文档。

**Step 3（兜底）：只有直接读取失败时才切分。**只有 PDF 确实超大，例如一本书、高分辨率扫描件或数百页文档，或者 PDF 已损坏、直接 Read 报错时，才用 Ghostscript 按页范围切分：
```bash
mkdir -p paper_name/
for i in {0..9}; do
  start=$((i*5 + 1)); end=$(((i+1)*5))
  gs -sDEVICE=pdfwrite -dNOPAUSE -dBATCH -dSAFER \
     -dFirstPage=$start -dLastPage=$end \
     -sOutputFile="paper_name/paper_name_p$(printf '%03d' $start)-$(printf '%03d' $end).pdf" \
     paper_name.pdf 2>/dev/null
done
```
然后逐份读取这些页范围文件，逐步建立对文档的理解。

## 错误处理协议

**如果直接读取失败**，原因是文件损坏或超大，就退回 Step 3，按页范围切分。

**如果某个片段处理失败：**
1. 记录有问题的片段，例如「Chunk p021-025 failed」。
2. 尝试再切成 1-2 页的小块。
3. 如果仍然失败，跳过该片段并记录缺口。

**如果切分失败：**
1. 检查 Ghostscript 是否已安装：`gs --version`。
2. 尝试替代方案：`pdftk paper.pdf burst output paper_%03d.pdf`。
3. 如果全部失败，请用户手动上传指定的页范围。

## 多份文档与一份文档是两个不同的问题

上述指引只针对**一份**论文：直接读取并翻页，上下文窗口足以宽裕地容纳它。

**上下文开销不能按文档数量简单外推。**一次加载约 10 份大 PDF，已经反复触发 `Prompt is too long`，迫使会话重置，并丢失此前完成的部分工作。

只要任务跨**超过两三份文档**，例如为一个语料库建立风格画像、分诊一整包审稿意见或扫读一批文献，就采用**每份文档一个子代理**的模式：

1. **为每份文档启动一个子代理**，各自使用独立上下文。
2. 每个代理**只读分配给自己的文件**，向磁盘写一条简短的结构化笔记（`notes/<name>.md`），长度为 300 字，使用固定 schema。
3. 每个代理只返回**文件名**，不返回内容。
4. 主会话随后**只读这些笔记**，再作综合。

这样，主上下文永远不会同时容纳超过一份文档的材料；一次失败也只会损失一个代理，不会损失整个会话。

> **开工前先数文档。**如果任务涉及的文档数量超过你两三次请求能读完的量，就在开工前决定使用子代理，不要等到第一次溢出。还要对照磁盘确认语料规模：用户说「我的论文」，磁盘上却查出十一份文档，与只有四份文档的任务并不相同。
