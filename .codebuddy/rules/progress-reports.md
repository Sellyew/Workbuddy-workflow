# 把 GitHub 当记忆 —— issue、进展报告与持久记录

**上下文窗口会结束。仓库不会。** 任何要紧的、只活在聊天记录里的东西，其实已经丢了 —— 你只是还没察觉。本条规则讲的是有意识地把记录从对话里搬出来、搬进仓库，让将来的某次会话、某位合作者或某位复现者真的能找到它。

三个持久存储，各存一类不同的东西：

| 存储 | 存什么 | 活多久 |
|---|---|---|
| **GitHub issue** | 已获证实的缺陷与悬而未决的问题，附证据 | 永久、可搜索、可链接 |
| **进展报告**（`quality_reports/`） | 做了什么、为什么、还剩什么 | 在磁盘上；本模板的 `.gitignore` 把 `session_logs/`、`plans/`、`specs/`、`merges/` 挡在 git 之外 —— 合作者需要的，用 `git add -f` 加进去 |
| **`MEMORY.md`** | 值得带到*下一个*项目的可推广经验 | 永久，已提交 |

其余一切 —— 推理过程、走过的弯路、对话本身 —— 都是一次性的，而且本该如此。

## 1. issue 是缺陷记忆

一条 issue 不是一条待办条目。它是**一份缺陷、它的证据、它的修复、以及该修复边界的持久记录**，写法上要让其中任何一部分都无法消失在某个分支、某段聊天或某条提交信息里。哪些工作该开 issue、证据标准、以及收尾评论：[`issue-ledger.md`](issue-ledger.md)。

**什么时候开：**当一次有边界的检查证实了某处违反了成文契约、统计规律、不变量、可复现性要求，或面向用户的承诺。

**为什么用 issue 而不用一个 TODO 文件：**它们可以跨年搜索，携带成串的证据，链接到修复它们的提交，能在每一次上下文重置后存活，而一条带有像样收尾评论的已关闭 issue 回答了*「我们是不是已经看过这个了？」* —— 就是那个否则会花掉一整天的问题。

**不要悄悄修掉一个已获证实的缺陷。** 无声的修复毁掉记录，下一个人就分不清一处刻意的改动和一次回归。

## 2. 进展报告是工作记忆

任何一次有分量的工作会话结束时，把发生了什么写到 `quality_reports/session_logs/YYYY-MM-DD_description.md`。Stop 钩子会自动起草一份；重点在于它**落在磁盘上**，而不在于它是你亲手打的。

一份有用的报告很短，回答四个问题：

1. **改了什么** —— 哪些文件，以及每个文件一句话的理由。
2. **决定了什么，为什么** —— 尤其是那些关掉了其他选项的决定。这是重建起来最贵、写下来最便宜的部分。
3. **试过什么又放弃了** —— *以及为什么失败。* 最有价值的一节，也是总被省掉的一节。它让下一次会话不再重走死路。
4. **还剩什么** —— 悬而未决的问题、被卡住的条目、显而易见的下一步。

更长寿的记录放在它旁边：`quality_reports/plans/` 放动手前的做法，`quality_reports/specs/` 放需求，`quality_reports/qualification/LEDGER.md` 放已被证明真能查出东西的部分，`quality_reports/merges/` 放发布时的报告。这些里只有 `LEDGER.md` 默认被提交 —— 模板的 `.gitignore` 把 `session_logs/`、`plans/`、`specs/` 和 `merges/` 留在本地，所以合作者需要的就用 `git add -f` 加进去。

> **在需要它之前就写。** 趁推理还活着时写的报告只要五分钟。一个月后从 diff 重建，要一个小时，而且是错的。

## 3. `MEMORY.md` 是经验记忆

issue 记住*这一个*缺陷。进展报告记住*这一次*会话。`MEMORY.md` 记住的是你在**另一个项目上**会想知道的东西。

提升是有意识的，不是自动的：原生自动记忆累积机器本地的观察，而 [`/promote-memory`](../skills/promote-memory/SKILL.md) 会在任何东西被提交前，对候选跑一个五批评者的议会。每次的检验都一样：

> *一个别的领域的研究者，fork 了这个模板，知道这件事会不会过得更好？*

如果是，它就是一条经验。如果它关于这台机器、这个数据集，或这一周，它就留在本地。

## 4. 更正记录

当先前报告过的某个断言被证明是错的，**更正走在最前面** —— 摆在下一份报告的第一句，而不是后面某份报告里的脚注。一份悄悄不再提某个已撤回发现的记录，比一份从未提过它的记录更糟，因为前者读起来是一致连贯的。

当结果以更高保真度重跑时，新产物*明确地***取代**旧的，而前身原样保留，作为记录。

## 5. 推送后的仓库就是状态报告

每个阶段落地就提交并推送 —— **包括失败，明确标注**。这样一位合作者、第二台机器，或三周后的你，只需要 `git pull` 就知道事情到哪一步了 —— 通过提交、issue 和你已提交的那些记录（本模板里会话日志和计划是 gitignored 的；别人需要的就强制加进去）。不用发状态邮件，不用写摘要，不用信任谁的记忆。
