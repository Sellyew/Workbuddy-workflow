# 把 GitHub 当记忆 —— issue、进展报告与持久记录

**上下文窗口会结束，仓库不会。**重要信息如果只留在聊天记录里，实际上已经丢失，只是你尚未察觉。本规则要求主动把记录从对话搬进仓库，让以后的会话、合作者或复现者能够找到它。

三个持久存储分别保存一类信息：

| 存储 | 存什么 | 活多久 |
|---|---|---|
| **GitHub issue** | 已获证实的缺陷与悬而未决的问题，附证据 | 永久、可搜索、可链接 |
| **进展报告**（`quality_reports/`） | 做了什么、为什么、还剩什么 | 保存在磁盘上；本模板的 `.gitignore` 将 `session_logs/`、`plans/`、`specs/`、`merges/` 排除在 git 之外，合作者需要的文件用 `git add -f` 加入 |
| **`MEMORY.md`** | 值得带到*下一个*项目的可推广经验 | 永久，已提交 |

其余内容都是一次性的，包括推理过程、走过的弯路和对话本身，也应该如此。

## 1. issue 是缺陷记忆

issue 不是待办条目，而是**一份缺陷及其证据、修复和修复边界的持久记录**。记录必须完整，任何一部分都不能只留在某个分支、某段聊天或某条提交信息中。哪些工作该开 issue、证据标准和收尾评论，见 [`issue-ledger.md`](issue-ledger.md)。

**什么时候开：**一次有边界的检查证实某处违反成文契约、统计规律、不变量、可复现性要求或面向用户的承诺时，就开 issue。

**为什么用 issue 而不用 TODO 文件：**issue 可以跨年搜索，串联证据，链接修复提交，并在每次上下文重置后保留。一条带有像样收尾评论的已关闭 issue，还能回答*「我们是不是已经看过这个了？」*，避免再花一整天重复排查。

**不要悄悄修掉一个已获证实的缺陷。**无声修复会破坏记录，使下一个人无法区分刻意改动和回归。

## 2. 进展报告是工作记忆

任何一次有分量的工作会话结束时，都把工作情况写入 `quality_reports/session_logs/YYYY-MM-DD_description.md`。Stop 钩子会自动起草一份；关键是报告**落在磁盘上**，而不是必须由你亲手输入。

有用的报告应当简短，并回答四个问题：

1. **改了什么**：涉及哪些文件，每个文件用一句话说明修改理由。
2. **决定了什么，为什么**：尤其要记录那些排除其他选项的决定。这类决定事后重建最贵，当下记录最便宜。
3. **试过什么又放弃了**：还要说明*为什么失败*。这是最有价值、也最常被省略的一节，能避免下次会话重走死路。
4. **还剩什么**：列出悬而未决的问题、被卡住的条目和显而易见的下一步。

需要保留更久的记录放在旁边：`quality_reports/plans/` 保存动手前的做法，`quality_reports/specs/` 保存需求，`quality_reports/qualification/LEDGER.md` 保存已经证明能查出问题的部分，`quality_reports/merges/` 保存发布时的报告。其中只有 `LEDGER.md` 默认提交；模板的 `.gitignore` 让 `session_logs/`、`plans/`、`specs/` 和 `merges/` 留在本地，合作者需要某份文件时，用 `git add -f` 加入。

> **在需要它之前就写。**趁推理仍然清晰时写报告只要五分钟；一个月后再从 diff 重建，不仅要一个小时，而且会出错。

## 3. `MEMORY.md` 是经验记忆

issue 记录*这一个*缺陷，进展报告记录*这一次*会话，`MEMORY.md` 则记录你在**另一个项目上**也会需要的信息。

候选经验必须经过人工筛选，才能纳入长期经验记忆，不会自动进入其中。原生自动记忆会累积机器本地的观察，而 [`/promote-memory`](../skills/promote-memory/SKILL.md) 会在提交任何候选之前，让五位批评者审查。每次都问同一个问题：

> *一个别的领域的研究者，fork 了这个模板，知道这件事会不会过得更好？*

如果答案是肯定的，它就是一条经验；如果它只关乎这台机器、这个数据集或这一周，就留在本地。

## 4. 更正记录

如果先前提报的断言被证明有误，**下一份报告的第一句就要更正**，不能把更正藏到后来某份报告的脚注里。悄悄不再提及一项已撤回的发现，比从未提及它更糟，因为前者会让整份记录显得始终一致。

用更高保真度重跑结果后，新产物要*明确***取代**旧产物，同时原样保留旧产物作为记录。

## 5. 推送后的仓库就是状态报告

提交和推送分别需要明确授权；两项都获批后，才在每个阶段落地后提交并推送。无论是否获得授权，失败都要记录并明确标注。未获授权时，以 **verified** 状态和验证证据交回，不自行提交或推送。这样，合作者、第二台机器或三周后的你只需 `git pull`，就能通过提交、issue 和已提交的记录了解进展。本模板将会话日志和计划设为 gitignored，别人需要时就强制加入。无需另发状态邮件、另写摘要或依赖任何人的记忆。
